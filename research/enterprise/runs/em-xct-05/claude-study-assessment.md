## Useful conclusions to carry into reconciliation

The suggested minimum is narrower than Codex's provisional five-object outline: export a ContextPackageProposal and a separate JointDisclosureReview, with PackageMember embedded. This is a strong candidate because proposer, reviewer, serving host and records custodian have different authority and lifecycles. Keep current serving decisions and physical disposal outside this companion. A single-object projection can refer to a genuine aggregate object, while a package merely collects projections. Review binds exact component membership, audience, purpose, source revisions and shapes. Prior releases and side channels need explicit consideration.

All four registry candidates receive a disposition. The study supplies 19 question routes, 10 invariants, synthetic startup/group/AI scenarios and a five-facet table. These are research proposals, not executed tests or inherited parent conformance.

## Corrections and unresolved design issues

| Study claim or proposal | Codex assessment and implementation consequence |
|---|---|
| WM-XCT-020 has no published specification digest | Retrieval gap, not catalogue fact. Runtime supplies sha256:47aa90ca48b7e367f61c30e454fd7859ba2dc7e2b998bbd4541acb6eda81b9bd for 0.3.0-research.1. DAT-004 and KNW-012 runtime entries are published/installable; inspect complete specifications/holds before any adoption. Existing authority work also references XCT-001. Preserve the study's genuine limitation. |
| None of the compared schools covers combined-release risk | Too broad. Codex directly read NIST SP 800-188 printed page 33, which explicitly discusses repeated releases and combinations with external information. The proposed companion may operationalize a record boundary, but it does not invent this concern. |
| SingleObjectProjection is already an executable profile of WM-XCT-003 | Unestablished. The parent is a semantic draft and excludes runtime execution. Compare exact field meanings before claiming a profile or inherited validation. An original reference with semantic alignment remains an option. |
| Proposal digest covers every field except proposal_id and status | Underspecified and potentially self-referential because proposal_digest is itself a field. Freeze an explicit digest body and encoding; bind the governed identity/header where scope matters. Keep lifecycle events/current state outside an immutable content body if necessary. |
| Same proposal digest guarantees the same validation result | Only with the same complete validation inputs, including accepted pins and profile/configuration version. Current host validity can change independently. Do not promise input-body-only determinism for a configuration-dependent validator. |
| cleared-with-conditions may suppress a member | Suppression changes the exact reviewed component set. Require a new proposal/review or a precisely defined reviewed alternative; never silently mutate the package while reusing its digest. Unexecuted conditions cannot count as satisfied. |
| A maximum-age note substitutes for an atomic host snapshot | A disclaimer does not resolve a check-to-delivery race. For any claimed live-serving gate, require a host freshness/transaction contract or refuse to assert readiness. The first metadata-only companion may describe the integration without claiming it exists. |
| review_applies checks only valid_until | Check valid_from as well, using an explicit interval convention and trusted current time. Current review withdrawal/invalidation and reviewer authority also need a trusted host state. |
| Host classifications are a subset of permitted-field labels | The pseudocode conflates the selected field scope with all source classifications and may ignore newly applicable schemes. Define exact per-selected-field current assignment and applicable-scheme coverage. Do not turn mere subset inclusion into authorization. |
| Nonrecursive path selection automatically prevents nested disclosure | A selected object-valued node can still carry a subtree. A narrow implementation must use a proven leaf/value boundary or remain metadata-only. Unsupported arrays, relationships, wildcard paths and transformations need explicit rejection or separately audited adapters. |
| Reviewer must always differ from proposer | Separation of duties is a host governance choice, not a universal ontology invariant. A one-person startup cannot meet this rule. Model actual roles and any self-review transparently; allow stronger profiles to require independent review. No implied independence from different aliases. |
| Opaque retention references suffice for all storage decisions | Useful for a first proposal boundary, but not for actual retention/disposition readiness. `none-declared` does not mean no applicable obligations. Unknown custody, trigger or hold remains a restricted unresolved condition; do not invent dates or claim disposal. |
| WM-XCT-035 is another team's model, so nothing can be designed | The catalogue stub is not an ownership prohibition. A separately researched original retention contract could be designed later under this program. It must not pretend to inherit a nonexistent published specification. |
| DPV differences imply edition inconsistency | The study's different edition summaries are not enough to prove concepts were removed or contradicted. Codex's initial DPV retrieval failed. Preserve a source-verification hold until the exact editions and terms are read directly. |

VERDICT: ACCEPT WITH LIMITS

BLOCKERS: none.

LIMITS:
- `displayCache` guard is correct for the stated cases: `None`/`"Acme"`/non-dict fail the `isinstance` test; `{}` and any missing `authoritative` fail `cache.get("authoritative") is not False`; identity comparison (not `==`) correctly rejects `0`; extra keys fail `set(cache)-{"authoritative","values"}`; non-string map values fail the `any(...)` clause, which is safely short-circuited behind the `values`-is-dict check. Schema mirrors it (`additionalProperties:false`, `const:false`, string-valued `additionalProperties`).
- Evaluator does not check that `values` **keys** are strings. Unreachable via JSON input (keys are always strings) but reachable for in-process callers passing native dicts; JSON Schema cannot express it either. Residual, non-blocking.
- New tests cover empty/null/string/unstructured cache and the accepted form, but not `authoritative: true`, non-string `values` entries, or an extra key inside `displayCache`. Those paths are correct by inspection, untested by the suite.
- Docs requirement is met in both places: model-spec.md ("checks closed record structure only… Schema validity does not imply profile conformance… Production adopters must apply both layers") and adoption-limits.md ("structural only… evaluator's semantic checks are mandatory"). Limit: the statement lives only in prose; `counterparty.schema.json` itself carries no `$comment`/`description` saying so, so a consumer resolving the `$id` alone sees no warning.
- Set-scoped projection is not weakened. Roles, scopes, contacts and segments are each filtered on `setRef == set_ref`; contacts additionally require their role and scope refs to be in the already set-scoped active maps, and `validate_profile` rejects cross-set contact wiring. Provenance is read from the anchor set only. The `superseded` set is computed globally, but `validate_profile` forces `supersedesRef` targets into the same set, so no cross-set suppression is reachable; this is an invariant coupling worth keeping if that check ever changes.
- Pre-existing, not a regression from either fix: a role with `supersededByRef` is dropped from `rolesAt` unconditionally, even when the successor binding is not yet active, which can yield a role gap in the current view. Also `$defs/Base` in the schema is unreferenced dead structure with an `id` field the profile does not use.

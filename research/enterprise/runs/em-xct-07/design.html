EM-XCT-07 · Design proposal D1

Enterprise Action Requests

Describe an immutable request, the current permission to execute it, and the evidence of its outcome.

Provisional design, not an installable model release. This is Codex's D1 proposal, prepared before Claude's recovered study completed. Both initial studies are now available in the research evidence; boundary reconciliation and frozen implementation audits remain pending. The earlier 24-test prototype does not implement the complete design below.

Bundles, Layers, Findings and Questions

B1 · Intent and identity

L1 · Definition and proposal

F01 · Exact action meaning

  • Which immutable definition revision governs the parameters?
  • Does the host resolve those exact bytes?

Artifact: Versioned definition reference, digest and closed parameter schema.

Proposed action: Resolve the pin; reject a digest mismatch or unsupported operation before admission.

F02 · Proposal has no execution power

  • Who suggested the operation?
  • Has separate authenticated submission occurred?

Artifact: Advisory ProposalEvent and explicit later request context link.

Proposed action: Record the suggestion; require host submission and current execution permission before any effect.

F03 · Definition lifecycle

  • Is the definition admitted for a first effect now?
  • What happens after retirement?

Artifact: Trusted definition availability record and versioned retirement policy.

Proposed action: Deny new first effects under a retired definition; evaluate replay/read under current policy without re-execution.

L2 · Request and exact content

F04 · Intended-operation identity

  • Is this the same intended operation?
  • Can it be referenced while pending and after completion?

Artifact: Immutable ActionRequest object and original SubmissionEvent.

Proposed action: Admit one independent identity; require a new identity for a semantic change.

F05 · Exact ordered parameters

  • Does reordering labels alter intent?
  • Which byte rules prevent ambiguous hashes?

Artifact: Canonical intent bytes, algorithm version and digest.

Proposed action: Validate closed input; preserve arrays and Unicode code points; compare both bytes and hash.

F06 · Immutable versus current context

  • Which values describe intent?
  • Which must be refreshed on each attempt?

Artifact: Intent, separate current host decisions and unchanged original admission.

Proposed action: Exclude current decision IDs/times from retry identity; bind actor, principal, target, definition and purpose exactly.

B2 · Representation and current permission

L3 · Roles and scope

F07 · Actor and principal

  • Who acts and on whose behalf?
  • Can a startup use the same party for both?

Artifact: Distinct actorId/principalId and trusted session binding.

Proposed action: Match authenticated fixture actor; permit equal roles without manufacturing another party.

F08 · Bounded direct delegation

  • Does the principal currently have the scope?
  • Is delegated scope no wider?

Artifact: Separate principal/delegate scope records, verified basis reference where used and decision evidence.

Proposed action: Intersect action/resource/purpose/time/audience/Dimension scope; reject unsupported chains and impersonation.

F09 · Issuer and accountability

  • Who may install scope?
  • Does an owner or title itself authorize execution?

Artifact: Trusted fixture governor, issuer standing and accountable-party reference.

Proposed action: Accept policy changes through the trusted host; retain accountability separately from permissions.

L4 · Execution, disclosure and revocation

F10 · Current execution decision

  • Which policy revision permitted this attempt?
  • Was it current inside the transaction?

Artifact: AttemptEvent with nonportable decision evidence and evaluation time.

Proposed action: Re-evaluate after acquiring the write transaction; serialize policy changes with effect commit.

F11 · Result disclosure

  • May the caller see a cached receipt now?
  • Do errors expose existence or conflicts?

Artifact: Current read decision and sanitized outward response contract.

Proposed action: Check disclosure before revealing receipt, replay, digest or detailed errors; test identical withheld responses across internal states.

F12 · Revocation and known time

  • Did revocation commit before execution?
  • Is remote freshness actually guaranteed?

Artifact: Local transaction order, policy revision and host freshness limits.

Proposed action: Deny under current local policy; preserve past receipts; do not claim knowledge of unobserved remote revocation.

B3 · Execution and recovery

L5 · Retry and atomic local effect

F13 · Namespace and key retention

  • Where is the key meaningful?
  • Can a retired key or request ID be reused?

Artifact: Durable key-to-intent mapping and tombstones.

Proposed action: Enforce key and request-ID uniqueness; stop on missing state or unexpected executor epoch.

F14 · Concurrent delivery

  • Can two attempts commit two effects?
  • Does retry preserve the original receipt?

Artifact: Transactional effect, receipt and attempt log with unique constraints.

Proposed action: Serialize independent connections; commit one effect, retain one receipt and distinct attempts.

F15 · Resource version

  • Is this a first effect or a retry after later work?
  • Does the expected revision still apply?

Artifact: Original precondition, before/after revisions and retained receipt.

Proposed action: Locate a committed request before checking current revision; require compare-and-set for a new effect.

L6 · Cancellation, uncertain response and compensation

F16 · Cancellation race

  • Did cancellation win before effect commit?
  • Is the request terminal?

Artifact: Authorized DispositionEvent in the execution transaction order.

Proposed action: Cancel pending work; reject contradictory receipt/disposition histories and cancellation after effect.

F17 · Lost response

  • Did the transaction commit despite timeout?
  • Is absent state actually the latest complete history?

Artifact: Original receipt, caller observation and governed continuity evidence.

Proposed action: Perform a fresh authorized read; preserve unknown caller knowledge until reconciled; stop after untrusted restoration.

F18 · Compensation

  • Which receipt is being compensated?
  • Has any intervening update occurred?

Artifact: New request/key, typed receipt link, before-value and exact prior after-revision precondition.

Proposed action: Re-authorize a new operation; reject cross-resource links, forged receipts and intervening revisions.

B4 · Evidence and adoption

L7 · Observation and whole history

F19 · Receipt versus observation

  • Is this a committed receipt or someone's report?
  • Does performance prove duty fulfilment?

Artifact: Distinct ReceiptEvent and OutcomeObservationEvent with issuer and evidence.

Proposed action: Derive execution state from trusted receipts/dispositions; leave obligation fulfilment to its own process.

F20 · Corrected knowledge

  • Which earlier observation is corrected, by whom and when?
  • Does correction alter the effect?

Artifact: Append-only same-observer/request chain with retained predecessors.

Proposed action: Validate the full chain; append a correction without replacing observations or receipts.

F21 · Consistent history

  • Are subjects, pins, attempts, outcomes and clocks consistent?
  • What proves current completeness?

Artifact: Retained native records plus semantic validation report and host continuity context.

Proposed action: Reject orphaned, branched, duplicated or contradictory histories; distinguish archive validity from admission and completeness.

L8 · Native binding and migration

F22 · Native representation

  • Which record is the request object?
  • Which occurrences are actual Events?

Artifact: Object/Event projections, nested schemas and export manifest.

Proposed action: Validate outer and nested/history contracts; avoid a fake aggregate host or duplicate request-state fact.

F23 · Adoption and legacy import

  • Can a Task, Contract, WriteGrant or document become executable?
  • Who authorized conversion?

Artifact: Staging/proposal mapping and explicit host submission.

Proposed action: Import as untrusted context; never infer action authority from labels, source priority or past acts.

F24 · Release and recovery limits

  • Which tests ran?
  • What must the real host supply, and can an old database be detected?

Artifact: Frozen pins, native fixtures, independent audits and continuity runbook.

Proposed action: Publish the implemented audited boundary; retain restore/epoch limits and package verification evidence.

Whole-object facets

ActionRequest
identity-class
Independent immutable intended operation; unique requestId/key; native object, not an occurrence or grant.
direct-properties
Definition pin, actor/principal, namespace, target/revision, purpose/deadline, ordered parameters and optional links.
recognition-observation
Exact admitted canonical bytes and submission; execution state derived from trusted events.
capabilities-behaviour-actions
Submit once, attempt, cancel pending work, authorized read, compensate by new request; no intent edit.
context-evidence
Host policy, external definition/basis, admission, resource/receipt history and retention/continuity limits.
ProposalEvent
identity-class
Advisory occurrence identified by eventId; no request or permission implied.
direct-properties
Proposed definition, target, purpose, parameters, suggested principal, proposer and clocks.
recognition-observation
Recorded suggestion with source and optional predecessor; never execution evidence.
capabilities-behaviour-actions
Record or supersede through a new advisory event; submission is a separate operation.
context-evidence
Source material, potential principal and later request link; document instructions are untrusted context.
SubmissionEvent
identity-class
Original admission occurrence for one immutable request; exactly one per request.
direct-properties
Request ID, intent digest, admitted definition pin and trusted submission instant.
recognition-observation
Matches retained request and admitting host; duplicate imports do not make new submissions.
capabilities-behaviour-actions
Record authenticated admission; cannot itself produce the resource effect.
context-evidence
Trusted host, canonical bytes and submission policy; archive shape alone proves no admission.
AttemptEvent
identity-class
One execution/replay occurrence for an admitted request; eventId, distinct from effect ID.
direct-properties
Operation, outcome, fresh decision evidence/time and request pin.
recognition-observation
Distinguished denied/stale/replayed/committed outcomes in retained history; private diagnostics stay private.
capabilities-behaviour-actions
Attempt under current scope or replay without another effect; no widening or grant issuance.
context-evidence
Transaction order, current policy, session, definition availability, receipt and disclosure rules.
ReceiptEvent
identity-class
Unique authoritative receipt of the local effect; native Event plus separate effect identity.
direct-properties
Before/after revisions and ordered values, request/definition pins and successful attempt.
recognition-observation
Trusted through the retained transaction; historical value is not current resource state.
capabilities-behaviour-actions
Authorized read/replay and compensation reference; no overwrite or effect undo.
context-evidence
Executor, transaction boundary, precondition, retry history and bounded storage assumptions.
DispositionEvent
identity-class
Terminal no-effect disposition for pending request; native Event.
direct-properties
Cancel/expire/precondition reason, request pin, instant and current governance decision.
recognition-observation
Valid only without receipt and according to serialized lifecycle; deadline acts before materialization.
capabilities-behaviour-actions
Cancel, materialize expiry or reject precondition; cannot cancel completed effect.
context-evidence
Trusted host, deadline/resource evidence, authorization and execution race order.
OutcomeObservationEvent
identity-class
Observer's knowledge assertion, distinct from effect and execution state.
direct-properties
Reported unknown/success/failure, evidence, observer, clocks and optional corrected Event.
recognition-observation
Retains known-at history; same-observer chain updates interpretation without erasing records.
capabilities-behaviour-actions
Append permitted reports/corrections; cannot execute, grant, discharge duty or replace receipts.
context-evidence
Request, observer provenance, retained predecessor, evidence and admission/disclosure policy.

Falsifiable invariants

  1. A ProposalEvent cannot enter the execute path and cannot create a receipt.
  2. Every admitted request has exactly one immutable intent, one namespace/key binding and one original submission.
  3. A reused request ID with a changed key or intent is rejected; a reused key with changed bytes is rejected.
  4. A first effect requires current exact scoped execution permission and a valid half-open deadline inside the local transaction.
  5. Delegated effective scope is a subset of both principal scope and delegate scope; roles and descriptive provenance alone never authorize.
  6. A request has at most one effect ID and one authoritative receipt; concurrent same-key deliveries cannot commit two effects.
  7. The effect, retained deduplication binding and receipt are committed together or rolled back together within the local database.
  8. A replay appends an attempt with fresh decision evidence, preserves the original receipt and cannot overwrite an intervening resource revision.
  9. Current disclosure denial yields no receipt, digest, existence, conflict or replay details, including cached responses.
  10. Policy revocation and cancellation take effect according to the same local transaction serialization order as execution.
  11. An observer correction preserves the targeted history and cannot create, retract or undo an effect receipt.
  12. A terminal disposition and a committed receipt cannot both be authoritative for one request.
  13. Retired keys and request IDs remain tombstoned; missing retained storage cannot silently initialize an empty executor.
  14. Compensation has a new identity/key, a verified prior receipt link, current authorization and a fresh resource precondition.
  15. Native outer schema success never substitutes for nested shape, digest, history, rights or transaction validation.
  16. A declared or imported authority reference cannot change trusted policy or authenticate its own issuer.

The next implementation must demonstrate these claims before its audits. Archive consistency, trusted admission, current authorization and storage continuity are separate requirements.

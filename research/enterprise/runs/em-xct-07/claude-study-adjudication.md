## Material corrections and open decisions

| Topic | Claude recommendation | Assessment and required disposition |
|---|---|---|
| Request identity | Acceptance Event identity is the request ID; a derived keySlotId is also an Event subject. | An Event anchor is semantically possible. However the native runtime resolves subjects to existing object or record IDs. An unmaterialized derived keySlotId is not such a record. Use a real retained subject, or keep the key in payload; do not invent a slot object solely to satisfy the envelope. D1's independent request object is another legitimate option, justified by pending intent/cancellation rather than field fit. |
| ActionDefinition | Exactly one new object master, a versioned operation definition. | Both providers favor a reusable definition, but the claim that this requires a new master needs comparison with legacy Function/Capability and Act's `actClass`, which were not in the original two-parent brief. The local seed inventory surfaced those drafts during this review. Do not equate a draft concept with an executable published contract, nor assume it does not exist. |
| Standing grant | A new DelegatedExecutionGrant Contract profile. | Potentially coherent, but Contract expressivity/native binding was not independently inspected and Ownership already describes a mandate artifact. The selected ownership comparison rules out reusing Fact Authority's source WriteGrant as generic execution permission. A second grant registry is not adopted without resolving that overlap. |
| Transaction claim | Several immutable files written in one file-lock section, with later reconciliation scanning resource revisions. | A lock serializes concurrent access but does not atomically commit those files or prove latest complete history. The study acknowledges crash windows. Its at-most-one claim needs explicit recovery, file durability and uniqueness enforcement; an arbitrary provenance field is not itself a uniqueness constraint. Prefer the actual single-transaction SQLite boundary for the bounded effect, or implement and test a complete file transaction/recovery protocol. |
| Absence as no-effect evidence | If no revision with requestId is found, reconcile as not_applied. | Safe only with an authoritative complete retained history under the same controlled effect boundary. A stale restored or incomplete local store can also contain no such revision after an effect occurred. D1's continuity counterexample still applies inside a local lock domain. A hash or local epoch alone does not prove latest history. |
| Retry disclosure | A denied reader may receive a duplicate-but-not-disclosable response; a changed binding yields a key-conflict error. | This conflicts with its own I9, which requires identical denied responses for absent/existing/conflict cases. Revealing duplicate status leaks existence even without the original content. The outward response must be uniform; detailed diagnostics belong in a privileged log. |
| Replay and attempts | Same-key duplicate creates no new attempt; attempts mean new execution tries after proven non-application. | This is a vocabulary choice. D1 uses separate delivery/replay attempt occurrences. The implementation must explicitly distinguish transport delivery, attempted execution and effect; it cannot silently switch definitions when reporting counts. |
| Deadline boundary | The study uses `t <= notAfter` and expires only when `t > notAfter`. | D1 uses half-open `t < expiresAt`. Either convention needs one explicit contract and boundary tests. Retain the half-open convention for consistency with other Enterprise packages unless a demonstrated interoperability need changes it. |
| Denial lifecycle | Denial is terminal and consumes the key; a later policy change needs a new key. | D1 leaves denied execution pending until deadline/cancel, while rechecking current policy on each delivery. Both can be safe; they have different business meaning. Choose explicitly rather than presenting consensus. Never repeat an already committed effect. |
| One-use AI grant | Optional maxUses=1 in the AI example. | Scope matching alone cannot enforce a use count. This requires a separate authoritative, concurrent, durable counter tied to committed effects and a defined retry rule. Defer it or implement it inside the same transaction; a supplied integer is not proof of remaining uses. |
| Array invariant | Reordering any array changes its digest. | Only a changed ordered sequence must change canonical content. Permuting equal elements can leave the same sequence and digest. Tests must not demand a false mathematical property. |
| Facets and event count | Five general facets and “eight” Event profiles. | The final package needs the five exact protocol facet keys. The proposed payload list includes additional paired proposal/cancel types; enumerate the actual exported types instead of inheriting an inconsistent count. |
| Test claims | Its case matrix labels planned cases “Implemented.” | No delivered EM7 implementation or executed acceptance results support that wording. Treat all those rows as proposed requirements. The existing 24 transaction tests and fourteen D1 shape negatives are separately scoped actual experiments. |

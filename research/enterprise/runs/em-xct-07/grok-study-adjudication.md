# Codex assessment of the independent Grok study

Status: initial assessment, pending a substantive independent Claude study. This is not a consensus or an implementation audit. Grok's complete raw answer is retained unchanged with its manifest. Its opening reference to a converging team is provider text; the orchestrator has no evidence of a cross-provider consensus.

## Adopt as design requirements

Preserve the distinction between action definition, proposed intent, immutable request, attempt, observed effect and duty. Keep the executor, represented principal, accountable owner and observer as distinct roles whose values may coincide when justified. Reuse native Event for observations. Keep a fresh authorization check before first effect and a separate current disclosure check even for cached results. Declare the exact retry namespace and immutable intent binding; preserve array order. Keep historical evidence after correction or compensation. Require safe handling of unknown outcomes, key retirement and lost history. Restrict the first adapter to a reversible synthetic local effect; no arbitrary commands, network actions or credentials.

## Correct or reject before implementation

1. **Digest comparison is invalid.** Grok compares the supplied raw spec.yaml SHA-256 with the embedded synthesisSha256 and calls that a mismatch. These hash different artifacts. Independently downloaded public spec bytes match the local publication and the supplied raw-file digests. The embedded synthesis digest is not a replacement for a raw-file hash. Preserve Grok's uncertainty but reject its mismatch conclusion.
2. **Envelope fit does not decide identity.** Grok argues that ActionRequest cannot use an Event profile because request fields do not fit top-level native fields. They could fit the open payload. The decision must follow the identity/lifecycle of intent versus submission, not the absence of extra top-level properties. Native event subjects can also reference another record ID. Do not create a Request object merely for installer compatibility.
3. **Authority freshness must not change retry identity.** Grok includes accept-time authorityDecisionId/evaluatedAt in bound content and also requires a new evaluation at every attempt. Copying that design mechanically makes a legitimate retry conflict after a fresh decision. Bind the immutable intent; record independent current authority observations on attempts. An accepted snapshot may remain historical evidence without becoming a mutable retry input.
4. **A file lock is not an atomic commit.** Grok's pseudocode asks for request, retry record, field mutation and events to persist atomically but does not supply that transaction. A SET operation is not sufficient protection against crash plus interleaving changes: a second SET can overwrite a later legitimate value. The local demonstration should place the effect, deduplication state and receipt inside one actual database transaction, with retained history and resource-version checks. External effects remain outside that guarantee.
5. **Do not mint a new DelegationMandate master before comparing ownership semantics.** WM-XCT-001 was not read by Grok. Existing published fact-authority and ownership models may already own relevant assertions. A bounded reference to a trusted host's current, explicitly scoped delegation can be sufficient for the first action increment; full delegation registry semantics need their own complete comparison before any new master.
6. **Role distinctions do not imply universal identifier inequality.** The study correctly allows an actor and principal to coincide when acting directly, but some prose calls all seven parties distinct references. Model distinct role fields, then validate an explicitly chosen direct/delegated profile. The matrix example's mandate comes from VP-Finance while the represented principal is Finance-EMEA: that requires separately evidenced issuing authority. Do not silently equate owner, delegator and represented principal.
7. **Cancellation and reconciliation need complete state rules.** The state diagram forbids rejection of an accepted request while prose permits withdrawing an uncommitted accept. Unknown reconciliation is allowed only toward committed, despite a possible proof of no effect. The implementation must explicitly distinguish request cancellation before dispatch, observed no-effect and unresolved outcome; a missing record after history loss is not proof of nonexecution.
8. **Embedding does not make an identity disappear.** ActionProposal and AuthorityDecision are called embedded values while carrying independent IDs and lifecycles. Choose one explicit identity policy for each; optional artifact IDs do not automatically require enterprise masters, and schema shapes do not prove absence of identity.

Grok's source additions (Stripe and an IETF idempotency draft) are not adopted as normative without independent verification. Its declarations that a hypothetical package can be installed "now" describe a proposal, not an actual released package. The actual publication state remains no EM-XCT-07 model release.

## Next useful experiment

Before freezing a model, test a small isolated SQLite transaction: one scoped intent, one reversible synthetic resource update, one effect receipt, retained retry key, current policy and disclosure checks all within the same store. Inject a rollback between effect and receipt, simulate a lost response after commit, run two independent connections, change policy between deliveries, and preserve a retired key. This checks a technical feasibility hypothesis; it does not implement the entire metamodel, authenticate real users, prove power-loss resilience or grant publication readiness.

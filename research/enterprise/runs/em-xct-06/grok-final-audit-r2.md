## Defects (must distinguish from documented limits)

### L1 — Documentation drift on the tested runtime
- **Severity:** Low
- **Where:** `migration.md` vs `model-spec.md` / `spec.json` / `test-results.json`
- **Counterexample:** Migration text says “Python 3.11+”; the semantic contract and the supplied unit-report pin **3.12.14**.
- **Fix:** One tested interpreter line everywhere. Keep “3.11+” only if you add an explicit compatibility claim and a report for that interpreter.

### L2 — Native envelope integer cap is tighter than V3
- **Severity:** Low (latent compatibility)
- **Where:** `monetary.py` `bounded()` / `validate_native()`
- **Counterexample:** `abs(int) <= 9999` is applied to the whole native object/fact. A later writer field (sequence, size, rank, revision counter) outside ±9999 would be rejected as `integer-bound` even if the outer V3 validator accepted the envelope.
- **Fix:** Apply the integer cap to receipt-owned JSON only, or admit the V3 integer vocabulary explicitly.

### L3 — Golden examples are generated by the test runner
- **Severity:** Low (process / freeze hygiene)
- **Where:** `test_monetary.py` `__main__` writes `examples/*.json` and `test-results.json`
- **Counterexample:** Re-running unit tests rewrites the frozen examples. A different library or interpreter can silently retint the “golden” bytes.
- **Fix:** Separate generation from verification; freeze example bytes and fail if they differ.

No High/Critical implementation defect found in the supplied text for signs, ties, stages, same-currency/context equality, source-slot uniqueness, immutable ID conflict, predecessor pin, rehash+replay, version fail-closed, or distinct existing/incoming issuer admission.

## Adversarial checks (claimed invariants vs this text)

**Decimal signs / ties / stages.**  
`round_units()` implements floor / ceiling / toward-zero / half-away-from-zero / half-even on the increment *count*, then multiplies back. Startup `0.495×3`, increment `0.01`, half-even: per-item `1.50`, after-sum `1.48` — matches the fixtures and acceptance narrative. Matrix `-1.025 + 2.075` per-item half-even → `-1.02 + 2.08 = 1.06` with signed residual `-0.01`. Negative-zero inputs are refused; zero output is unsigned. Stage is only `per-item` | `after-sum`.  
Oracle mapping is to `Decimal.quantize` on `token/increment`, not a claim of IEEE/ISO cash-rounding law. That mapping is internally consistent in the test *source*; the 200-case pass report is an assertion, not a fact this audit re-ran.

**Precision limits.**  
Input grammar + digit cap: 36 digits, 18 fraction places. Output cap 57 digits is the right order of magnitude for `256 × (36 nines)` plus an 18-place increment, and `test_boundaries` encodes that case. Rational fields are wider than the decimal output cap. Increment must be positive and lexically exact; `'0.10'` vs `'0.1'` is the same Fraction and a different result scale — tested and honest.

**Same currency, different context.**  
Complete `Currency` tuple (catalogue, edition, snapshotDigest, code, resolution) and complete `Context` (basis pin, `valuationAt`, `amountRole`) must match across inputs and policy. Code mismatch, edition mismatch, digest mismatch, basis mismatch, role mismatch, and `valuationAt` mismatch all refuse. Same ISO code alone does not pass. Aggregation *permission* is still a host fact.

**Source-slot identity.**  
`source.id` uniqueness inside one request; duplicate keys also refuse. Same amount from two slots is allowed. Slot truth/exactness/sign are not proved by decimal syntax.

**Immutable correction.**  
New id, exact `supersedes` pin, non-blank reason, same subject and issuer, `computedAt >=` predecessor, acyclic closure, missing pin → `supersedes-unresolved`. Branches retained; no winner. `issue()` does not look up the predecessor (no I/O); only `import_receipts` on a supplied complete register does. That split is stated.

**Rehash tampering.**  
`validate()` requires canonical digest of the receipt-minus-digest *and* `result == compute(request)`. Changing the total and resealing still dies on `replay-mismatch`. Acceptance’s nested overwrite (total `999`, new digest, new factId) is the right isolation: outer V3 can stay valid; companion must not.

**Version refusal.**  
`schemaVersion` const `0.1.0`, `additionalProperties: false`, unknown fields and `0.2.0` refuse. No silent migration.

**Native outer vs nested.**  
`validate_native()` binds object type/id/recordId, empty `previousRecordId`, restricted/active, fact path/factId/subject, empty fact `supersedes`, master/writer, disclosure digest, `validFrom == recordedAt == object.recordedAt`, and `recordedAt >= computedAt`. Acceptance lists exact error codes for those mutations. `outerAloneAcceptsBadArithmetic: true` is an advertised property, not a hidden hole.

**Host authority.**  
`allowed_issuers` / admitted issuer sets / `resolution: host-admitted` are caller assertions. Result `authority` is the const `calculation-only`. No payment, posting, IAM, or signature engine exists in this package. That is correct *only if* the host does not treat a sealed receipt as authorization.

**Register bounds vs claims.**  
256 inputs; 256 existing; 256 incoming; 256 unique merged ids; exact same-id replay does not consume a new slot. Unreferenced omitted leaves are undetectable without a prior snapshot. No retention/tombstone/current-selector implementation. Tests in source cover the 256 replay and the +1 refusal; the JSON pass reports remain unverified here.

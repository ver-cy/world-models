# Frozen semantic audit — EM-FIN-04

## Verdict

**Conditional accept of the decision; artifacts not publishable.** The supplied evidence does not disprove the intended decision, and it is preserved: profile WM-ECO-018 for the consolidated statement; keep **Consolidation Scope** and **Consolidation Run** as independent identifier-unassigned candidates (both carry lifecycles that outlive and precede any statement issue, and both satisfy the version-identity test in the supplied `identityTest` blocks); profile **Elimination Entry** on WM-ECO-016 within one consolidation book and one run; leave source ledgers, organizations, control, holdings and policy externally mastered; allocate no catalogue, model or runtime ID.

Three convergent studies agree on the allocation shape, so the allocation is not the weak point. The weak point is that the reconciled artifacts under-specify the fields their own invariants require. Grok's stated failure condition for the elimination profile (a run-scoped adjustment discriminator that does not share source-journal identity) is **unmet in the supplied artifacts** — this is a specification gap, not a disproof, so the profile stands with defect 7 as a hard gate rather than being downgraded. No additional root is justified by any defect below.

## Material defects

**1. Reference-direction inversion between the candidates and WM-ECO-018.** Both `allocation-candidate.json` files list WM-ECO-018 in `boundary.references` ("Statements citing a scope revision"; "Statements citing selected run outputs"), while the profile asserts that WM-ECO-018 cites consolidation outputs. That is a cycle, and it couples scope/run lifecycle to the statement issue lifecycle that both files `exclude`.
*Remediation:* delete the WM-ECO-018 entry from `boundary.references` in both files; append to each `boundary.excludes`: `"inbound statement citation (WM-ECO-018 cites this root; this root never references a statement issue)"`. Citation direction is recorded only in `profile-candidate.json.constraints`.

**2. Run requires a scope pin it does not declare.** `ConsolidationRun.required` includes `scopeRevisionRef`, but Consolidation Scope appears nowhere in the run's `boundary.references`, and `excludes` says only "scope identity". A required pin to an undeclared target is dangling. Nothing forbids pinning a `draft` revision either, which contradicts "Every run pins one immutable scope revision".
*Remediation:* add to run `boundary.references`: `{"target":"candidate:consolidation-scope","purpose":"Pinned immutable scope revision consumed by the run","allocationState":"unassigned"}`; change the excludes item to `"scope identity and scope lifecycle (pinned by reference only)"`; add run invariant `"A run pins exactly one scope revision whose status is approved or effective at the run knowledge cut; draft revisions are not pinnable."`

**3. Mastership leak: scope owns control evidence.** Scope `boundary.owns` includes `"control basis, authority and evidence"`, which contradicts `profile-candidate.json` constraint 3 and grok's "Holdings, policy and organizations are cited, not re-decided inside the consolidation model."
*Remediation:* replace that `owns` item with `"citation of control basis, authority and evidence as versioned external references"`; append to `boundary.excludes`: `"control assessment, voting-power determination and economic-ownership determination"`.

**4. Unsafe inference channel left open on WM-ECO-038.** The scope candidate labels WM-ECO-038 `"Ownership and control assertions"` while an invariant in the same file states that economic ownership, voting power, control and consolidation treatment are separate assertions. WM-ORG-012 is simultaneously demoted to `"Enterprise group context"`. This is exactly the inference grok's counterexample attacks (60% with protective rights only; de facto control below 50%), and no invariant blocks percentage-driven inclusion — only *common ownership* is blocked.
*Remediation:* set the WM-ECO-038 purpose to `"Equity holding assertions used as inputs only; never a control basis"`; set the WM-ORG-012 purpose to `"Control and inter-organizational relationship assertions"`; add invariant `"Neither an ownership percentage nor any threshold establishes or refutes membership; membership requires an evidenced control basis valid in the membership interval."`

**5. No knowledge-time field exists anywhere.** `ScopeRevision` carries only `effectiveFrom`/`effectiveTo`; `ConsolidationRun` carries only `cutoff`/`executedAt`. Yet both files assert that valid and knowledge time stay distinct, and the acceptance result requires reproduction at a prior knowledge time. The invariants are unsupported by any field, so prior-knowledge replay is unimplementable as specified.
*Remediation:* add required `recordedAt` (RFC 3339, explicit offset) to `ScopeRevision`; add required `knowledgeCutAt`, `periodStart`, `periodEnd` to `ConsolidationRun`; add to both invariant sets: `"Replay at knowledge time T resolves only revisions and pins whose recordedAt is less than or equal to T, never current configuration."`

**6. Membership is an unstructured field, so purpose and mid-period intervals are unrepresentable.** `ScopeRevision.required.membership` has no declared structure. `purpose` sits on `ConsolidationScope`, while the invariant demands purpose per membership — making silent purpose reuse representable despite the `silent-purpose-reuse` fixture. Grok's mid-period full→equity change cannot be expressed at all.
*Remediation:* replace `membership` with `membershipRefs` and add object `ScopeMembership`: `identity ["consolidationScopeId","revision","memberOrgRef"]`; `required ["purpose","consolidationApproach","controlBasisRef","authorityRef","evidenceRefs","validFrom","recordedAt"]`; `optional ["validTo","ownershipAssertionRefs","nonComparabilityMarker"]`. Add invariant `"Statutory and management purposes never share a membership list, even when membership overlaps."`

**7. The elimination profile has no adjustment discriminator — grok's declared failure condition.** `profile-candidate.json` constrains eliminations "to one consolidation book and run" but names no field; claude-study records that WM-ECO-016 itself declares intercompany elimination unmodelled. Source and consolidation identity can therefore collapse, and `tolerance` is referenced by invariant while pinned nowhere.
*Remediation:* add a `profileFields` block for WM-ECO-016 with required `bookClass` (fixed value `consolidation`), `adjustmentClass` ∈ {`intercompanyRevenueCost`,`receivablePayable`,`investmentEquity`,`unrealisedProfit`,`dividend`}, `consolidationRunRef`, `scopeRevisionRef`, `counterpartyLegRefs` (exactly two, each `{bookRef, entryRef, lineRef}`), `matchKey`, `matchedAmount`, `unmatchedAmount`, `residualReason` ∈ {`timing`,`fx`,`inTransit`,`cutoff`,`none`}, `tolerancePolicyRef`, `initiatorRef`, `authorizationRef`. Add constraint: `"If WM-ECO-016 cannot carry bookClass and consolidationRunRef without sharing source-journal identity, this profile fails and no identifier is allocated."` Add hold: `"WM-ECO-016's self-declared omission of intercompany elimination structure is unclosed in the base."`

**8. The balancing invariant is incoherent.** "Entries balance within one book, currency, scope and tolerance" (local-evidence invariant 8, run invariant 6) treats scope as a balancing dimension. A perimeter is not a balancing dimension; this weakens the no-cross-ledger-balancing rule it is meant to restate.
*Remediation:* replace in all three artifacts with: `"Each entry balances within one consolidation book and one currency, inside one run, against one pinned tolerance policy revision; no cross-book or cross-currency netting; scope is not a balancing dimension."`

**9. Required run pins target masters that do not exist, with a contradictory home for mapping.** `mappingRefs` and `rateSetRef` are required; the only candidate home offered is WM-KNW-012 ("Accounting, mapping and transformation policy revisions"), while the holds simultaneously declare chart-of-accounts/mapping and FX rate set unallocated. `taxonomyRef` and `tolerancePolicyRef` are demanded by invariants but absent from the field list, and the run has no `contentDigest`, so its immutability is unverifiable. This is grok's version-addressability blocker.
*Remediation:* add required `taxonomyRef`, `tolerancePolicyRef`, `contentDigest`; re-type `mappingRefs`, `rateSetRef`, `taxonomyRef`, `tolerancePolicyRef`, `sourceRevisionRefs` as `ExternalVersionPin {masterRef|null, identifier, version, digest}` with `version` and `digest` required; narrow the WM-KNW-012 purpose to `"Accounting, consolidation-method and transformation policy revisions"`; add hold: `"Chart-of-accounts/group mapping, FX rate set, taxonomy, tolerance policy, intercompany match and trial-balance sets have no allocated master; they are carried as opaque external version pins and no identifier is allocated for them in this contour."`

**10. Lineage is one-directional and restatement semantics are missing.** `ConsolidationRun.optional` offers only `successorRunRef` — from a successor you cannot resolve the original, defeating "Restatement references and does not overwrite it". No `restatementClass`/`reason` field exists despite being required by the restatement section. `ScopeRevision.supersedesRevision` carries no reason.
*Remediation:* add to `ConsolidationRun.optional`: `supersedesRunRef`; make `restatementClass` and `restatementReason` required whenever `supersedesRunRef` is present. Add to `ScopeRevision`: `changeReason`, required whenever `supersedesRevision` is present. Add invariant to both: `"A successor resolves its predecessor and never replaces it; both editions remain resolvable."`

**11. Lifecycle is attached to the wrong object, and `failed`/`retired` are unspecified against citation.** `ConsolidationScope` holds the full `draft…superseded…retired` lifecycle while `ScopeRevision` — the object actually superseded — has no status field, so defect 2's pinnability rule has nothing to read. The run lifecycle admits `failed` and `retired` with no rule on whether their outputs are citable, so a statement's pin can dangle or cite a failed execution.
*Remediation:* set `ConsolidationScope.lifecycle` to `["draft","active","retired"]`; add `ScopeRevision.required.status` with `lifecycle ["draft","approved","effective","superseded"]`. Add run invariants: `"A failed run emits no citable output."` and `"A retired run remains immutable and resolvable for every statement that already cites it; retirement never invalidates an existing citation."` Add the same resolvability invariant for retired scope revisions (present in the scope file, absent in the run file).

**12. Authorization and segregation are unenforceable as specified.** `ConsolidationRun.executorRef` is optional, there is no run-level `authorizationRef`, and `TransformationStep.authorizationRef` is optional — while governance requires authority for run execution, elimination posting, post-cutoff adjustment, scope change, issue and restatement, with initiator/authorizer separation. The scope candidate has `authorityRef` but no initiator.
*Remediation:* make `executorRef` and `authorizationRef` required on `ConsolidationRun`; make `TransformationStep.authorizationRef` required when the step is a post-cutoff adjustment; add required `initiatorRef` and `authorizerRef` to `ScopeRevision`. Add to both invariant sets: `"initiatorRef differs from authorizerRef, or compensatingControlRef is present."`

**13. The profile states a correction as accomplished while holding it as pending.** `profile-candidate.json` constraint 1 asserts "WM-ECO-018 owns report and issue identity and cites consolidation outputs without executing consolidation", which the base does not currently declare; the same file holds that the WM-ECO-018 boundary "require[s] correction". A profile cannot narrow a base by assertion.
*Remediation:* rewrite constraint 1 as: `"WM-ECO-018 must be narrowed to report and issue identity plus citation of consolidation outputs; until that narrowing is recorded in the base, this profile is non-installable."` Add hold: `"WM-ECO-018's serviceLayers role claiming ownership of entity perimeter, ledger and position bindings, eliminations, transformations and lineage contradicts its own out_of_scope declaration; unresolved."`

**14. Missing publishability holds and fields.** `profile-candidate.json` carries neither `canonicalPublishable` nor `allocationState`. None of the three artifacts records: all bases being non-canonical reviewable drafts with four single-provider waivers and dual-provider timeouts on WM-ECO-018/017/038 and WM-ORG-012; the WM-ECO-018 COMPOSE WM-ECO-017 versus WM-ECO-017 REFERENCE WM-ECO-018 direction conflict (absent from the run candidate, which references WM-ECO-017); WM-ORG-012 parentage and WM-ECO-038 extension semantics (absent from the scope candidate, which references both); WM-REC-002 unfrozen parent; WM-ECO-018 marking every checklist dimension covered while admitting no external review. The explicit no-installability statement appears only in `local-evidence.md`.
*Remediation:* add `"canonicalPublishable": false, "allocationState": "unassigned"` to `profile-candidate.json`; append all six holds above to the `holds` array of whichever artifacts reference the affected base (run: composition direction, WM-ECO-017 evidence; scope: WM-ORG-012 parentage, WM-ECO-038 extension; all three: base draft status, waivers/timeouts, WM-REC-002); append to all three: `"No installability, canonical-completeness or publication-readiness claim is made."`

**15. Stale hold contradicted by the supplied evidence.** All three artifacts hold "Independent Grok review is pending" while `grok-study.raw.md` is supplied and records a conditional accept with five named blockers.
*Remediation:* replace that hold in all three with: `"Independent review recorded (grok-study.raw.md): conditional accept of the allocation. Open blockers: elimination adjustment discriminator; scope control-evidence version, perimeter type and effective date as consumable pins; version-addressable external references; restatement as a new run citing the original without a new identifier; separate statutory and management membership lists."` No further provider run is requested or required.

**16. Duplicate mastership of the comparability bridge.** Scope `owns` "effective periods and comparability lineage" plus `ScopeRevision.comparabilityBridgeRef`, while the run `owns` "contained run outputs and comparability bridge". Two roots master one artifact, and the bridge has no declared structure in either.
*Remediation:* assign the bridge to Consolidation Run alone (it decomposes pinned figures across two runs). Change the scope `owns` item to `"effective periods and revision lineage"`; delete `comparabilityBridgeRef` from `ScopeRevision.optional` and add `bridgeRequired` (boolean, true whenever `supersedesRevision` is present). Add run object `ComparabilityBridge`: `identity ["consolidationRunId","comparedRunRef"]`; `required ["scopeDelta","methodDelta","rateDelta","activityDelta","nonComparabilityMarker"]`.

**17. Non-deterministic and boundary-crossing fixtures.** (a) Run fixture `two-ledger-run` names "rate set FX1" where the shared acceptance scenario uses `FX-2026Q2`. (b) `paired-elimination` states no amounts, currencies, book or tolerance, so "documented FX residual" is not decidable. (c) `late-adjustment` asserts statement-version behaviour and cites "statement A1", both outside the run boundary, which excludes statement issue lifecycle. (d) `current-rate-replay` names no replay operation and no knowledge time. (e) Both fixture files key cases to the mutable `candidateName` and omit `contourId`. (f) `profile-candidate.json` carries six constraints and zero fixtures.
*Remediation:* add `"contourId":"EM-FIN-04"` and `"candidateKey":"candidate-allocation-offline-consolidation-scope"` / `"candidate-allocation-offline-consolidation-run"` to the two fixture files; state every amount, currency, RFC 3339 instant with offset, book, mapping, rate-set and tolerance identifier literally; change `FX1` to `FX-2026Q2`; rewrite `late-adjustment.expect` to `"A successor run R2 is created; R1 remains immutable and resolvable at its own knowledge cut."`; create `candidate-profile-offline-consolidated-statement/fixtures.json` with `"format":"vercy-enterprise-allocation-fixtures/v1"`, `"contourId":"EM-FIN-04"`, `"candidateKey":"candidate-profile-offline-consolidated-statement"` and carry the statement-version assertion there; add an `invariantRefs` array to every case naming the invariants it exercises.

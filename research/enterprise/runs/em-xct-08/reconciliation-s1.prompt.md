## Newly checked boundary

Enterprise Identity 0.1.0 binding.schema.json defines `kind` with exactly `enum: ["person", "organization", "user-account", "service-account"]`. Its Python ALLOWED_KINDS has the same four members. Its SourceBinding is an immutable carrier in an identity assertion, not a mapping from an arbitrary board to a Project. Therefore literal reuse of that schema for Project or Dataset would fail. Its semantic exact-key rule can be aligned, but no executable schema embedding or exactMatch is available for these kinds. Source object kind and target subject kind also differ legitimately: board ABOUT Project is not board IS Project.

The platform's Virtual-Projection.md says reads do not mutate canonical state; source freshness/provenance are required; hot and cold projections differ. Its native projection will describe one explicitly owned aggregate register; that is not a business Project value or a second source master.

## Proposed reconciled decisions; challenge defects rather than inventing unanimity

1. Boundary: one companion Enterprise Source Synchronization contract with no runtime imports. New narrow RecordSubjectMapping expresses purpose-qualified ABOUTNESS, not IdentityAssertion. QualifiedSourceKey is a local support value aligned with exact qualified identifiers, explicitly NOT an instance of Identity's four-kind schema. Admission checks that the trusted target catalogue's subject kind equals expectedTargetKind and that the trusted mapping policy allows the pair (sourceObjectKind, expectedTargetKind, purpose). Two boards may both map to one Project. No subject creation, merge, fact selection, remote fetching, or business effects.

2. Three generations remain distinct. SourceInstanceGeneration changes only on tenant/environment namespace replacement or loss of instance continuity; RecordGeneration changes for a recycled key/new record incarnation; SyncEpoch changes for checkpoint invalidation/reinitialization. A 410 or cursor expiry alone does NOT prove new record identity or force replacement of every mapping. A PK change yields a different qualified source key; possible continuation is a steward proposal, not automatically a new whole-source generation. Unknown continuity is explicit.

3. Mapping identity anchors source lineage, target subject, expected kind, purpose and issuer. State revisions can propose/activate/dispute/retract that same claim. A target/source/purpose/kind change requires a NEW mapping ID with a correction link and old claim retraction, in one governed transaction where applicable. Enforce at most one active mapping per (source lineage, purpose), ACROSS mapping revisions and target kinds, not uniqueness including revision. Historical cuts keep the old mapping. Original occurrences retain their admitted mapping revision; no retroactive rewrite.

4. Separate acquisition scope from mapping application. Scope fingerprints include source instance generation, resource, scheme version, filter, projection, principal visibility, connector interpretation version, schema fingerprint, and stream mode. First release supports one unpartitioned stream per scope; many scopes may coexist. Partition/global state is refused. Mapping revisions do not alter the acquisition key or cursor. Each accepted occurrence pins its mapping revision or explicit unmapped/disputed status. Replay identity (scope, epoch, batchKey) plus exact immutable body bytes includes the original mapping pins. A mapping-only correction therefore cannot create a new intake effect by retrying the old batch; reprocessing is a separately identified future activity. Changes to key extraction or actual source-query/schema interpretation require a new scope/epoch.

5. Coverage is a SnapshotRound identity plus immutable scope fingerprint, expected page chain/terminal page, missing/error declarations and consistency-kind/evidence. The per-round snapshot token/LSN is evidence, NOT a component that must be equal between consecutive rounds; otherwise no two real snapshots could compare. A complete round means all declared pages accounted at that claimed consistency boundary; it is not source-authenticity proof. Candidate absence requires two complete comparable rounds, equal acquisition scope, and adequate consistency evidence; best-effort/no consistency evidence only yields insufficient-context. No automatic deletion or retirement even on explicit source deletion. A partial-page miss, inaccessible, removed-from-scope, explicit source-deletion and absence-in-comparable-round remain separate conclusions.

6. A committed SyncCheckpoint is an immutable receipt-linked progress edge only. Source-emitted/staged proposals are attempt inputs, never checkpoints. One local SQLite transaction commits accepted occurrences, durable quarantine descriptors, conservation manifest, receipt and head CAS. The transaction implements local destination acknowledgement; it does not claim an independent external destination or source transaction. `received = accepted + quarantined`; accept-loss is refused in 0.1.0. Empty batches require explicit zero declaration. The operator must supply a stable batch identity for retry; the register cannot deduplicate arbitrarily repaginated source deliveries by magic.

7. SQLite current-head CAS and an epoch-local writer-fence revision are distinct. Trusted administration can advance fence revision without accepting a batch, fencing out a still-running stale worker. Begin-immediate serialization and exact fence equality prevent two local commits of the same predecessor. There is no clock-based distributed lease. A committed identical replay after later progress may return the original receipt AFTER current authorization; no effects. A changed body using that key yields a retained restricted conflict; it cannot overwrite or advance. A closed epoch allows only authorized historical receipt lookup, never resume or new commit. A copied stale database cannot detect its own staleness: an external recovery anchor is a host duty.

8. Current authorization precedes receipt/idempotency/existence lookup. A revoked writer gets the same generic denial whether the key exists or not, never an old protected receipt. A currently authorized writer with no read permission may receive a minimal own-operation acknowledgement, not a register dump; historical receipt read requires current read permission. Restricted denial telemetry is host-owned outside canonical intake history. Source grants, steward standing and EFA source priority are not destination intake permission. The local fixture can demonstrate policy ordering with synthetic host configuration, not a real IAM guarantee.

9. RecordOccurrence identity uses (committed batch identity, input ordinal), not merely key+payload digest: the same record can occur twice in one page with meaningful ordering. An occurrence stores qualified key/generations, operation/source availability, content evidence reference, observedAt, sourceEventTime only when supplied, and optional correctionOf. Trusted recorded/committed times and local sequence are separate. No cross-clock total order. A correction is a new occurrence preserving old evidence and knownAt cuts, not a changed old capture. Payload digest proves byte consistency at most, not truth, authenticity or privacy.

10. First release stores protected opaque references to source payload and resume token evidence, no raw credentials/tokens/endpoints/payloads. It may carry a supplied digest labelled algorithm+protectionClass, but no per-host HMAC/re-key service or confidentiality guarantee. All operational exports remain restricted including keys, counts, times and digests. Low-entropy digest disclosure is unsafe; do not claim hash = anonymization. Round-trip preserves opaque references and their protection namespace; another host may validate the archive yet MUST refuse resume until it independently establishes current token access, current authority and latest head. Unknown version or conversion losing generation, history, quarantine, mapping pins or scope is refused with a LossReport. Validation is not resumption.

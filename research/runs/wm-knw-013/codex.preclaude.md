# Codex pre-provider hypothesis for WM-KNW-013

## Boundary

Constraint / Requirement Rule should be an entity for one stable formal or
formalizable normative rule. It owns rule identity, expression, applicability,
evaluation semantics, exception handling and revision lineage. Stakeholder need,
requirement record, policy, standard, control, test, validation result,
decision, evidence and enforcement remain external masters.

## Proposed structure

1. Rule identity, source expression, kind and normative force.
2. Scope, authority, applicability and temporal activation.
3. Predicate, operands, datatypes, units and logical composition.
4. Traceability, requirement relations, exceptions and conflicts.
5. Evaluation, outcomes, evidence, lifecycle and revision.
6. Governance, access, retention and interoperability.

Each bundle should contain two layers and four findings. Each finding should ask
three model-specific questions and define one data element and one serial
evidence artifact. Ten functions should register, formalize, classify, bind
applicability, compose, approve or activate, evaluate, record an exception or
resolution, revise or supersede and project an authorized view.

## Expected hard points

- Requirement, constraint, business rule, policy rule and validation shape need
  explicit profiles rather than one universal execution semantics.
- RFC normative keywords express requirement levels only when the governing
  document explicitly adopts them.
- Syntactic validity, rule satisfaction, conformance, compliance and accountable
  approval are distinct.
- Unknown, indeterminate, not applicable, waived and violated outcomes differ.
- Exceptions and precedence must be bounded, attributable and time-qualified.
